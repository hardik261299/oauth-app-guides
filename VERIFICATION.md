## Second pass (2026-10-28): unconfirmed claims resolved against sources

Items first written as "general knowledge" were looked up and the guides updated:

- **Google 100-user cap: confirmed, and stricter than I wrote.** It is a lifetime cap of 100 *new users* after the unverified-app screen is shown, "cannot be reset or changed" ([source](https://support.google.com/cloud/answer/15549945)). Guide now says so.
- **Google 7-day testing refresh token: confirmed, with an exception I had missed.** It does not apply when scopes are limited to name, email and profile ([source](https://developers.google.com/identity/protocols/oauth2#expiration)).
- **New finding: 100 refresh tokens per account per client ID**, oldest silently invalidated. Added to the guide; relevant to anyone re-authorizing in a loop.
- **Slack public distribution: confirmed.** It is called *unlisted distribution*, is activated under Manage Distribution, and does **not** need Marketplace review; Marketplace listing is only recommended for commercial apps ([source](https://docs.slack.dev/distribution/)). This changes the Slack wait from "unknown" to "none for unlisted distribution". Admin approval per workspace was added as a blocker-type nuance.
- **Still unresolved:** Google verification turnaround, Google security-assessment cost, Slack Marketplace review time/requirements (provider pages checked do not state them).

## Spot-check of a live-generated guide: Zoom (2026-10-28)

Guide generated by the deployed app (https://oauth-app-guides.vercel.app/, "Zoom", 7 docs pages read). I then re-fetched the cited pages myself and searched their **full** text (the agent only sees the first 9,000 characters of each page) for every requirement, step and blocker. Method limit: this is phrase matching plus reading the surrounding text, not a full manual read of every page, and it is one guide, not a statistical sample.

**Right (checked against page text)**
- Prerequisites: account owner, account admin or the "Zoom for developers" role; how an admin enables that role (User Management > Roles > Role Settings > Advanced features), used correctly as a blocker fix.
- Separate development vs production credentials; OAuth redirect URL and OAuth allow list are both marked "(required)" on the page.
- Steps 1-5 (Marketplace > Developer > Build an app > General app; Basic Info incl. Admin-managed vs User-managed; Scopes with a per-scope description; Local Test > Add App Now > Allow) match the "Create" page.
- Scope descriptions matter: the page says adding a scope submits a request to Zoom's Security Review team, who may reject unnecessary scopes. Matches the "scope rejection" blocker.
- Domain validation methods (TXT record, HTML file, meta tag, manual request) are all listed on the submission page. (My first search pattern missed two of them; reading the page showed the guide was right.)
- Approval = "sometimes" is correct: the review-process page says private and beta apps do not require review.
- **Wait time "Not published" is correct.** None of the 7 pages states a review duration (only an unrelated 90-day refresh-token expiry), so the guide did not invent one.

**Wrong or weak**
- **Run-to-run inconsistency.** An earlier generation of the same app said approval "yes" and stressed a mandatory review; the later one says "sometimes". The page supports "sometimes". Output is not deterministic, so a shared guide can differ from a regenerated one.
- **"~30 min" hands-on time has no source.** It is a model estimate and is not tagged as such. Estimates should be labelled "estimate".
- **Domain validation is listed as a general requirement** but is only needed when submitting for review (public/unlisted apps). The steps section places it correctly under submission; the requirements list does not.
- **Agent/you split is optimistic.** Steps 2-5 are labelled "agent can do", but every one needs a signed-in Zoom developer account in the Marketplace UI. Nothing was attempted by an agent, so this is an untested claim.

**Missed (present in fetched pages, absent from the guide)**
- Refresh tokens expire after 90 days (OAuth page), which affects how often users must reconnect.

**Not verifiable from the pages**
- Review turnaround; fees or plan restrictions (guide lists both under "uncertain", which is accurate).

**Design gap this exposed.** The server downgraded a "confirmed" claim only if its *source URL* was not fetched; it did not check that the page *text* supports the claim. A wrong claim attributed to a real fetched page would have stayed "confirmed".

### Fixes made after the spot-check (re-tested on Zoom, 2 runs each)

| Issue found | Fix | Result on re-run |
|---|---|---|
| Confirmed claims not tied to page text | A confirmed requirement must carry a verbatim quote; the server checks it appears in the fetched page (case/punctuation-insensitive, min. 20 chars) and otherwise downgrades to unconfirmed. The quote is shown under the claim, and a banner says how many were downgraded. | Works: 1 unsupported claim downgraded in one run. |
| Missed 90-day refresh-token expiry | Cause: the agent only saw the first 9,000 characters of each page and that sentence is at character 10,604. Page cap raised to 16,000 and the prompt now asks for token lifetimes. | Both runs now include "Refresh tokens expire after 90 days". |
| Domain validation shown as a general requirement | New structured field `appliesTo` (always / publishing); the UI tags publishing-only items. | Both runs tag domain validation "publishing". |
| Unsourced "~30 min" | Hands-on time is always labelled "Estimate:" (agent and curated guides). | Labelled in all runs. |
| Optimistic agent/you split | Prompt restricts "agent" to code/API work, and the server downgrades any "agent" step worded as console navigation to "both". The page also states labels are a plan, not a tested result. | Console steps now "developer"/"both"; "agent" only on code steps. |
| Run-to-run inconsistency on approval | Temperature set to 0 and an explicit rule for yes/sometimes/no with the condition stated. | "sometimes" in all 4 re-runs. |

**Still not fixed:** output is not fully deterministic (hands-on estimates still differ between runs, e.g. 30 min vs 1-2 hours; the set of requirements varies). The console-step guard is a keyword heuristic, so a mislabelled step with unusual wording could pass. Quote checking proves a quote exists on the page, not that the claim paraphrases it correctly.

## Corrections and findings from checking

- **Slack docs moved.** `api.slack.com/authentication/oauth-v2` returns a 302 to `docs.slack.dev/authentication/installing-with-oauth`. Guide cites the new URL.
- **Slack Marketplace review guide could not be loaded** (guessed URL returned 404). Review requirements and timing are therefore listed as unverified rather than asserted.
- **GitHub docs say nothing about review.** I wrote "no documented review", not "no review", and kept org-level third-party restrictions as unconfirmed. The same page recommends considering a GitHub App before an OAuth app, which became a decision step in the guide.
- **LinkedIn docs are internally inconsistent.** The auth-flow page's sample requests use legacy `liteprofile`, while the permissions table lists `profile`/`email` via OpenID Connect. The guide follows the permissions table and flags the discrepancy.
- **The first Google help pages I read did not state** the 100-user cap or testing-mode token expiry, even though these are widely repeated, so they were first left `unconfirmed`. Other pages later confirmed both (see the second pass above); verification turnaround is still not published.
- **Notion's authorization URL is gated on review submission.** This is the key nuance for planning: you cannot start the user flow until the connection is submitted. Review duration is not documented on the page read.

## Not verified at all

- Real approval durations for any provider (providers largely do not publish them).
- Any behaviour that requires a signed-in console: exact UI labels, plan restrictions, fees.
- The optional Anthropic path (never run). The Gemini path was spot-checked on one app (Zoom, see above); Asana and other generated guides were not checked.
